신규 자산 3: 방향 enum + 시퀀스 묶음 + 디버그 설정

Step 3 의 모든 로직은 세 개의 새 데이터 타입 위에 선다. 로직(섹션 03 · 04)으로 가기 전, 이 세 자산을 실측값 그대로 정리한다. 세 자산 모두 module_name 이 비어 있는 프로젝트 콘텐츠(/Game/ALS/) 다.

★
실측 출처 project_query.get_asset_details (3 자산) + project_query.get_stats (인덱스 신선도) + animation_query.get_abp_variables (소비 측 타입 cross-check). 구조체 필드명 뒤의 _N_GUID 접미사는 UserDefinedStruct 의 내부 표현이며, 에디터 표시 이름은 접미사 앞부분(Forward 등)이다.

E_LocomotionDirections (UserDefinedEnum)

이동 방향 을 4 개의 이산 값으로 식별하는 enum. Step 2 의 E_Gait(속도 상태) 와는 축이 다르다 - 속도가 아니라 "어느 쪽으로 가는가" 다.

표시 이름값내부 이름
Forward0NewEnumerator0
Backward1NewEnumerator1
Right2NewEnumerator2
Left3NewEnumerator3
i
값 순서가 곧 Select 인덱스다 이 0/1/2/3 순서는 우연이 아니다. 섹션 04 에서 보듯 OnCycleUpdate 의 Select 노드 입력 핀이 NewEnumerator0~3 이름을 그대로 쓰고, S_DirectionalAnims 의 필드 순서(Forward/Backward/Right/Left)와 1:1 로 맞물린다. enum 엔트리 순서를 바꾸면 방향 매핑이 어긋난다.

S_DirectionalAnims (UserDefinedStruct)

"한 Gait 의 4 방향 시퀀스" 를 한 덩어리로 묶는 구조체. 측정된 필드는 4 개, 전부 UAnimSequence* (object), 기본값 None.

필드 (표시 이름)타입기본값
ForwardUAnimSequence*None
BackwardUAnimSequence*None
RightUAnimSequence*None
LeftUAnimSequence*None

이 구조체는 ABP_Layers 에서 두 개의 변수로 인스턴스화된다 (실측 - animation_query.get_abp_variables):

  • WalkCycleAnims : S_DirectionalAnims (category Cycle)
  • JogCycleAnims : S_DirectionalAnims (category Cycle)
↳
왜 enum 대신 struct 로 묶나 4 개 시퀀스를 개별 변수로 두면 Walk/Jog 마다 4 개씩 8 개 변수가 흩어진다. 구조체로 묶으면 "방향 묶음" 이 1 급 단위가 되어, Select 한 번으로 통째 고르고 방향 인덱스로 한 번 더 쪼갤 수 있다 (섹션 04 의 2 단 Select 가 정확히 이 구조 덕에 가능).

S_DebugSetting (UserDefinedStruct)

화면 디버그 표시를 켜고 끄는 bool 묶음. 측정된 필드 2 개, 둘 다 bool, 기본값 True.

필드 (표시 이름)타입기본값게이트 대상 (섹션 04)
ShowGaitDataboolTrueCurrentGait 문자열 출력
ShowLocomotionDataboolTrue속도/각도/방향 + 속도 화살표

이 구조체는 ABP_Base 의 변수 DebugSettings : S_DebugSetting (category Debug) 으로 들어가 있다. 즉 디버그 on/off 가 코드 분기가 아니라 데이터(구조체 필드) 로 노출된다 - Step 2 의 S_GaitSetting 이 CMC 파라미터를 데이터로 뺀 것과 같은 패턴.

cross-check: 정의와 소비처가 일치하는가

메모리 규약(핵심 식별자는 2 액션 이상으로 확인)에 따라, 세 자산의 정의를 소비 측에서 다시 확인했다.

cross-check S_DirectionalAnims 필드 ↔ Select 핀
get_asset_details 가 준 필드 GUID(Forward_6_5457BEF7..., Backward_7_3C54CC03..., Right_8_66D729BE..., Left_9_30CE7736...)가 OnCycleUpdate 의 Select_1/Select_2 입력 핀 connected_to 에 같은 GUID 로 그대로 나타난다 (get_node_details). 정의와 사용이 일치.
cross-check E_LocomotionDirections ↔ ABP_Base 변수
enum 4 엔트리(get_asset_details) ↔ ABP_Base.LocomotionDirection : byte (get_abp_variables) ↔ CalculateLocomotionDirection 의 출력 ReturnValue : byte + 내부 Switch on E_LocomotionDirections (get_graph_summary). 세 액션이 같은 타입을 가리킨다.
cross-check S_DebugSetting ↔ DebugSettings 변수
struct 2 필드(get_asset_details) ↔ ABP_Base.DebugSettings : struct:S_DebugSetting (get_abp_variables) ↔ Debug 그래프의 Branch 2 개가 각각 한 필드를 게이트 (get_graph_summary, 섹션 04).
측정 한계 find_references 가 비어 있다
세 자산 모두 project_query.find_references 의 referenced_by 가 [] 로 응답했다. UserDefinedEnum/Struct 의 역참조는 Monolith 응답에 안 잡힌다. 그래서 소비처 확인은 위처럼 소비 BP/ABP 의 변수·노드 실측으로 대신했다 (이 quirk 는 섹션 05 에 정리).
★
