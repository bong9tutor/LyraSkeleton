SECTION 07 · 의도 분석

저자가 BP 에 남긴 설명과 디버깅 일지

Step 3 의 코멘트가 "왜 이렇게 설계했나" 였다면, Step 4 의 코멘트에는 새로운 종류가 섞인다 - 실패를 기록한 디버깅 일지다. "이렇게 했더니 버그가 났고, 원인은 이거였고, 이렇게 고쳤다" 가 그래프 안에 적혀 있다. 이 섹션은 변경/신규 그래프의 함수 설명과 노드 코멘트를 모아, 특히 디버깅 코멘트가 가르치는 것을 분석한다. 아래 인용은 모두 원문 그대로이며, 오타("애미네이션", "상테", "StopDistnace", "SeqenceEvaluator")와 띄어쓰기도 보정하지 않았다 - 저자의 실제 메모를 그대로 보존하는 것이 학습 자료로 더 정확하기 때문이다.

의도 분석 (1) 디버깅 기록 - Step 4 의 핵심 자료

Step 4 에는 "무엇을 하는가" 가 아니라 "무엇이 잘못됐고 어떻게 고쳤는가" 를 적은 코멘트가 셋 있다. 학습 프로젝트에서 이런 일지는 정답 코드보다 값지다 - 같은 함정을 피하게 해 주기 때문.

디버깅 (1) MaxTransitionsPerFrame 3 → 1 (LocomotionSM 노드)

섹션 02 에 전문을 실은 코멘트. 요지: Start → Cycle 전이가 "직전 프레임 방향 vs 현재 프레임 방향" 을 비교하는데, 엔진 기본값(한 프레임에 전이 3 회 평가)에서는 2 회차 평가 때 "직전 프레임" 변수가 이미 갱신돼 비교가 깨졌다. 결과는 "Forward 만 정상, 좌우/후방에서 Start 스킵". 해결은 평가 횟수를 1 로 제한.

i
이 일지가 가르치는 것 "프레임당 1 회 갱신되는 변수를, 프레임당 여러 번 평가되는 곳에서 읽으면 시간 의미가 깨진다." LastLocomotionDirection 같은 "직전 프레임" 변수는 갱신 주기와 소비 주기가 같아야 한다. 저자는 이 교훈을 "■ 주의 - 이 값을 다시 올리면 위 버그가 재발하므로 1로 유지할 것" 으로 못박아, 미래의 자신(또는 학습자)이 되돌리지 못하게 했다.

디버깅 (2) / (3) 캐싱 타이밍 - OnInit 콜백은 ABP_Base 데이터를 못 쓴다

OnInitStartAnims 와 OnInitPivotAnims 에 거의 같은 내용의 코멘트가 각각 달려 있다. 둘 다 같은 함정을 가리킨다 - 레이어 진입(OnBecomeRelevant) 콜백이 BlueprintThreadSafeUpdateAnimation 보다 먼저 호출되어, ABP_Base 가 캐싱한 Acceleration2D 가 아직 0 이라는 것.

OnInitStartAnims - PropertyAccess 노드 코멘트 2 개 (원문 그대로) 
# 짧은 fix 메모
"fix: ABP_Base 에 캐싱된 Acceleration 2D 가 항상 0 이라 직접 CMC 에서 Get"

# 긴 원인 분석 메모
"- 애니메이션 State 호출 타이밍이, BlueprintThreadSafeUpdateAnimation 함수
  호출 보다 먼저 호출 되어 캐싱 되는 Data 를 사용 할 수 없는 것으로 추정
- 추정이 맞는 것으로 확인됨, 근거는 3가지.
첫째, UE5 애니메이션은 게임 스레드 캐싱 → 워커 스레드 평가의 2단계 구조이고,
      노드 함수(OnBecomeRelevant)와 캐싱 갱신의 순서가 어긋날 수 있음
둘째, 전이/노드 평가 시점에 변수가 기대대로 반영 안 되는 건 알려진 이슈
셋째, 라이라 자체가 \"진입 시 선택 / 업데이트 시 갱신\"을 분리하고
      진입 시점 데이터 유효성을 신경 써 설계"
OnInitPivotAnims - PropertyAccess 노드 코멘트 (원문 그대로) 
"SequenceEvaluator 의 OnBecomeRelevant 콜백 함수 호출 타이밍에
 ABP_Base 에서 미리 캐싱해 놓은 가속도(Acceleration2D) 값을 사용 할 수 없다.
 이유는, ThreadSafeUpdate 호출전에 해당 함수 콜백이 호출되기 때문."
↳
이 일지가 가르치는 것 섹션 04 에서 OnInitStartAnims / OnInitPivotAnims 가 왜 ABP_Base.Acceleration2D(이미 계산해 둔 값)를 안 쓰고 Calculate Direction 으로 CMC 에서 직접 가속도를 다시 구하는지 - 그 답이 이 코멘트다. 진입 콜백은 BTSUA 보다 먼저 도니 캐싱값이 신선하지 않다. 저자가 마지막 줄에 적은 "라이라 자체가 '진입 시 선택 / 업데이트 시 갱신' 을 분리" 가 이번 Step 의 설계 원칙을 정확히 요약한다 - 그래서 6 개 콜백이 전부 OnInit + OnUpdate 쌍이고, OnInit 은 진입 순간 유효한 데이터(CMC 직접 읽기)로 시퀀스를 고르고, OnUpdate 는 그 뒤 매 프레임 안전하게 캐싱값을 쓴다.

의도 분석 (2) "진입 시 선택 / 업데이트 시 갱신" 이 구조가 되다

디버깅 (2)(3) 의 교훈은 코멘트로 끝나지 않고 그래프 구조 자체가 됐다. Step 4 의 신규 레이어 콜백 6 개는 예외 없이 OnInit / OnUpdate 쌍이며, 역할이 갈린다:

콜백 종류호출 시점책임데이터 출처
OnInit*레이어 진입 시 1 회무엇을 재생할지 (방향·Gait 시퀀스 선택)CMC 직접 읽기 (캐싱 미신선)
OnUpdate*매 프레임어디를 재생할지 (Distance Matching 시간)ABP_Base 캐싱값 (신선)

저자는 이 분담을 OnUpdatePivotAnims 의 Comment 노드에 "Then 0: ... (무엇을 재생할지)" / "Then 1: ... (어디를 재생할지)" 로 한 번 더 명문화했다. 코멘트((2)(3)) → 구조(OnInit/OnUpdate 쌍) → 코멘트(Then0/Then1) 로, 같은 원칙이 세 번 반복해 못박혔다.

의도 분석 (3) 반복 관용구 - Step 3 에서 이어진 스레드세이프 Getter

Step 3 에서 분석된 "스레드세이프 Getter 관용구" 는 Step 4 에도 그대로 살아 있다. ABP_Base.GetCharacterMovement 와 ABP_Layers.GetBaseAnimBP 의 PropertyAccess / Return Node 코멘트는 다음과 같다:

유지 ABP_Base.GetCharacterMovement
PropertyAccess: "PropertyAccess 를 사용하는 이유는 UE5 애니메이션이 멀티 쓰레드(WorkerThread)로 동작하기 때문에 안정성을 위해 사용합니다." / Return Node: "Outputs 변수명은 반드시 ReturnValue 로 설정 해야 AccessProperty 에 노출 됩니다. (엔진 강제)" - Step 3 과 동일.
문구 변형 ABP_Layers.GetBaseAnimBP
PropertyAccess: "애님 BP가 멀티스레드로 돌기 때문에, 외부 데이터를 안전하고 빠르게 읽기 위해 Property Access를 씁니다" - Step 3 문서는 이 코멘트가 GetCharacterMovement 와 동일 문구라고 기록했으나, Step 4 에서는 요지는 같되 문장이 다르다. 저자가 그 사이 코멘트를 다듬은 것으로 보인다. Return Node 코멘트는 양쪽 동일.
새 관용구 "재생 위치를 0초로 리셋"
Step 4 에서 새로 반복되는 관용구. OnInitStopAnims / OnInitStartAnims / OnInitPivotAnims 의 Set Explicit Time 노드에 전부 "Sequence Evaluator의 재생 위치를 0초로 리셋합니다. (정지/시작/...) 애니메이션을 처음부터 시작하기 위함" 코멘트가 달렸다 - 세 OnInit 콜백이 같은 책임(진입 시 시퀀스를 0 초로 초기화)을 진다는 표시다.

의도 분석 (4) 레이어 그래프의 교육적 코멘트

섹션 05 의 레이어 그래프 코멘트는 디버깅 일지와 또 다른 종류다 - 기능 설명 + 셋업 체크리스트 + 설계 근거를 한 덩어리로 적은 교육적 코멘트다.

교육형 Warping 코멘트 = 설명 + 번호 체크리스트
Orientation / Stride Warping 코멘트는 둘 다 "이 노드가 무엇을 한다" 한 문단 뒤에 번호 매긴 주의사항(1~4)을 단다 - "Foot Definitions 가 비어 있으면 동작 안 함", "Min Root Motion Speed Threshold 로 억제" 같은. 단순 설명을 넘어, 이 노드를 다루는 사람이 빠지기 쉬운 함정까지 미리 적은 셋업 가이드다.
설계 근거형 PivotSM 코멘트 = "왜 이 구조인가"
PivotLayer 의 코멘트는 "왜 Pivot 만 전용 State Machine 인가" 를 시나리오(앞→뒤→앞→오른쪽)로 설명한다. "Pivot 애니메이션은 감속 → 회전 → 가속 이 함게 있어 ... 단순 교체는 모션 끊김" - 섹션 02 의 디버깅 코멘트가 "실패 후 수정" 이라면, 이건 "처음부터 이 구조를 택한 이유" 다.
참조표형 Dot Product 각도 대응표
PivotSM 안에는 Dot Product 값과 각도의 대응(1.0=0°, 0.5=60°, 0.0=90°, -0.5=120°, -1.0=180°)을 적은 코멘트가 있다. 전이 룰이 내적으로 방향 일치를 판정하므로(섹션 02·05), 그 판정값을 읽는 사람이 바로 각도로 환산하도록 둔 참조표다.
