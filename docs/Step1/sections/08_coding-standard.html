코딩 표준 핵심 정리

docs/CodingStandard.md 의 핵심 정책 압축. 네이밍·접두사·매크로·어서션·헤더·의존성. 전체 표준은 원문 참조.

1. Ls 프로젝트 접두사 정책

본 프로젝트의 모든 새 C++ 타입은 UE 타입 접두사(U/A/F/E/I/T/S) 뒤에 Ls 를 붙입니다.

접두사적용 대상본 프로젝트 예
UUObject 상속ULsAnimInstance, ULsWeaponComponent
AAActor 상속ALsCharacter, ALsPlayerController
F일반 클래스/구조체FLsLocomotionState
Eenum classELsWeapon, ELsGait
I추상 인터페이스ILsInteractable
SSlate 위젯SLsHudPanel
i
예외 - Ls 가 안 붙는 식별자 모듈 자체(public class LyraSkeleton : ModuleRules), API 매크로(LYRASKELETON_API), 모듈 진입 파일(LyraSkeleton.h/.cpp) 는 모듈 전역 식별자 라 LyraSkeleton 그대로.

1.1 부울은 b 접두사

bool bIsFiring;
bool bHasFadedIn;
bool bPendingDestruction;

1.2 파일 이름

파일명에는 UE 타입 접두사를 두지 않습니다. 단, 프로젝트 접두사 Ls 는 그대로 남깁니다.

  • ○ LsAnimInstance.h
  • × ULsAnimInstance.h
  • × AnimInstance.h

2. 자주 쓰는 매크로 형식

C++ · UPROPERTY / UFUNCTION 표준 양식 
UCLASS(BlueprintType, Blueprintable)
class LYRASKELETON_API ULsSampleComponent : public UActorComponent
{
    GENERATED_BODY()

public:
    UPROPERTY(EditAnywhere, BlueprintReadOnly, Category = "Ls|Sample",
              meta = (ClampMin = "0.0"))
    float SampleScalar = 1.0f;

    UFUNCTION(BlueprintCallable, Category = "Ls|Sample")
    void ApplySample(const FVector& InOffset);

private:
    UPROPERTY(Transient)
    TObjectPtr<UStaticMeshComponent> CachedMesh = nullptr;
};

2.1 Category 는 Ls|Subsystem 형식

Project | Subsystem 의 파이프 구분. 짧은 Ls 덕에 UPROPERTY 패널 폭이 절약됩니다.

2.2 UObject 멤버는 TObjectPtr

의도권장 형태
소유 또는 강한 GC 참조UPROPERTY() + TObjectPtr<UFoo>
비소유 약참조 (대상이 사라질 수 있음)TWeakObjectPtr<UFoo>
클래스 메타 참조 (강)UPROPERTY() + TSubclassOf<UFoo>
에셋/클래스 지연 로딩TSoftObjectPtr<T> / TSoftClassPtr<T>
함수 인자·지역 변수raw UFoo*

3. 문자열·정수형 별칭

문자열 리터럴

FString S = TEXT("Hello");

정수형

int 대신 int32. UPROPERTY 위에서는 강제.

FName / FString / FText

식별자/태그 → FName, 가변 문자열 → FString, 사용자 표시 텍스트 → FText.

이동 의미

MoveTemp(X) (= std::move), Forward<T>(X). std::move 직접 사용 금지.

4. 헤더 포함(IWYU)

  1. 멤버에 UFoo* 만 쓴다면 헤더에서는 전방 선언 (class UFoo;).
  2. 새 헤더의 첫 줄(저작권 다음) 은 #pragma once.
  3. .cpp 의 첫 #include 는 자기 자신의 헤더.
  4. UCLASS/USTRUCT 헤더의 마지막 include 는 항상 *.generated.h.

5. 어서션 - check vs ensure vs verify

check(C) Fatal
Shipping: 컴파일아웃 부작용금지

절대 깨지면 안 되는 프로그래머 가정. 실패 시 즉시 크래시. Shipping 빌드에서는 식 자체가 사라지므로 식 안에 부작용을 두면 안 됨.

  • BAD: check(SaveProgress()); - Shipping 에서 호출 안됨
  • GOOD: 결과를 변수에 받은 뒤 check(bSaved);
verify(C) Eval+Assert
Shipping: 식은 평가 부작용OK

식 평가가 항상 필요한 어서션. Shipping 에서는 식은 그대로 실행되고, 결과 검증만 생략. 부작용 있는 호출에 안전.

  • 예: verify(SaveProgress()); - Shipping 에서도 SaveProgress 는 호출됨
ensure(C) Soft Assert
Shipping: 평가+보고 부작용OK

비정상이지만 계속 진행 가능한 상황. 첫 발생 시 보고하고 흐름은 이어감. 처리 가능한 외부 입력 검증/에셋 누락 등에 사용.

  • 처리 가능한 비정상 상태에는 check 가 아니라 ensure + 폴백 경로 사용
!
고전 함정 
// BAD: Shipping 에서 SaveProgress() 가 호출되지 않음
check(SaveProgress());

// OK
const bool bSaved = SaveProgress();
check(bSaved);

// OK: 식 평가가 필요하면 verify
verify(SaveProgress());

6. 로깅

C++ · 모듈/서브시스템별 카테고리 
// .h
DECLARE_LOG_CATEGORY_EXTERN(LogLsAnim, Log, All);

// .cpp
DEFINE_LOG_CATEGORY(LogLsAnim);

// 사용
UE_LOG(LogLsAnim, Verbose, TEXT("Speed=%.2f"), Speed);
!
LogTemp 는 일회성 디버그에만, 커밋 전 제거. 영구적인 로그는 반드시 도메인별 카테고리(LogLsAnim, LogLsWeapon, …) 를 만들어 사용.

7. 들여쓰기·공백

  • 인코딩 UTF-8, 줄바꿈 CRLF, 들여쓰기 공백 4 칸.
  • 중괄호는 Allman 스타일 (여는 { 가 새 줄).
  • 한 줄 권장 100~120 자, 강제는 아님.
  • em dash (U+2014) 사용 금지 - ASCII 하이픈(-) 으로 대체. 본 프로젝트의 모든 문서/주석에 동일 적용.

8. PR 직전 체크리스트 (압축판)

  • 첫 줄 저작권, 헤더는 #pragma once, 마지막 include 는 *.generated.h
  • 접두사 (U/A/F/E/I/S + Ls) 와 부울 b 접두사가 일관
  • UPROPERTY/UFUNCTION 의 Category 가 Ls|... 형식
  • UObject 멤버는 UPROPERTY() + TObjectPtr<T>
  • 비싼 인자는 const T&, 싼 인자는 값
  • virtual 재정의에 override
  • 문자열 리터럴은 TEXT(), 정수형은 int32, std::move 대신 MoveTemp
  • LogTemp 가 남아있지 않음
  • check() 의 식에 Shipping 에 필요한 부작용을 두지 않음
  • Public 헤더가 노출하는 타입의 모듈이 PublicDependencyModuleNames 에 있음
  • 단일 분기라도 중괄호 생략 없음, switch 는 default: 와 의도된 [[fallthrough]];
  • em dash 가 포함되어 있지 않음 (코드 주석/로그 메시지/문서)
i
